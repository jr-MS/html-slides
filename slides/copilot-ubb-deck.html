// 09 — BUDGET SCOPES

Budget 怎么设：先选 作用域，再定 是否阻断

ENTERPRISE · 全企业总闸 适合做最高 spend cap / failsafe。官方说明：Enterprise-level budgets 会覆盖企业内来源，包括 cost centers。
ORGANIZATION · GitHub Org / 大团队 适合按事业部、研发组织、独立 GitHub Org 管控。组织预算可直接设置，但与 cost center 重叠时要谨慎。
COST CENTER · 财务核算 / 项目 / 试点人群 Enterprise 专属。可把 users、organizations、repositories 放进去，用于分摊成本和设置独立上限。
USER · 单个开发者的实际体验 每人先消耗 plan 自带 allowance；重度用户通常用 cost center、paid usage policy 或升级 Enterprise 来管理。
客户落地建议：先简单，后精细

大多数企业第一阶段：先设 Enterprise 总预算 + 开启告警，再按用户/重度人群观察用量。

业务复杂后：再增加 Organization 或 Cost Center，用于区分生产/研发/实验、项目组或试点团队。

避免过度重叠：官方建议不要无必要地叠加多个会阻断的预算，否则用户可能被意外拦截。

// 10 — BUDGET EVALUATION

预算判断逻辑：共享池 + Overage 分层约束

先用套餐包含额度；进入超额付费后，才同时检查 Enterprise / Org / Cost Center 等适用预算。

STAGE 1 · 共享包含额度

所有 license 带来的 allowance 先形成可用额度池。大多数日常使用先从这里消耗，不会立刻进入额外付费预算判断。

POLICY · 是否允许超额

Premium request paid usage policy 决定用户是否能在 allowance 用完后继续产生额外用量。

STAGE 2 · Overage 预算控制

进入超额付费后，适用的 Enterprise / Org / Cost Center / User 预算同时生效；任何一个到顶并启用阻断都会停止相关请求。

客户版理解：不是“全程短板”，而是共享池之后的 overage 阶段由适用预算共同约束。
